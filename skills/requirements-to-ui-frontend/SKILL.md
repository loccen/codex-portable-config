# Requirements To UI Frontend

## 概览

使用这个技能时，核心顺序是：需求或原型输入 -> 静态 HTML DEMO 还原 -> 浏览器截图对比原型 -> UI 设计师视角评分 -> 90 分以上通过 -> 基于通过的 DEMO 产出 UI 说明 -> 正式前端实现与验收。

不要跳过静态 HTML DEMO 校准层。它是保证正式前端高度还原原型图的关键动作。

## 工作流

### 1. 读取输入并确定还原目标

- 读取需求文档、原型图、已有 UI 说明、接口文档和当前工程实现。
- 明确本轮原型版本；如果用户指定 v3，就严格以 v3 为准。
- 建立页面清单、状态清单、关键交互、文案约束和静态资产清单。
- 区分两类内容：
  - 真实 DOM：标题、正文、表单、按钮、筛选、表格、列表、导航、弹窗文案。
  - 静态资产：插画、横幅、纹理、徽章、图标、装饰图。
- 对已有工程任务，先盘点路由、组件、样式 Token、接口层和构建命令，避免正式开发阶段破坏项目边界。

### 2. 生成或整理原型与资产

- 如果原型图尚不存在，使用 `$imagegen` 生成高保真原型和必要静态资产。
- 如果原型图已经存在，优先复用现有原型，不要为了流程完整而重生。
- 如果是多屏或长页面，按页面和状态编号保存，确保后续截图对比能一一对应。
- 进入正式工程的资产必须复制到项目目录，并检查白边、棋盘格、错误文字、错误 logo 和容器适配问题。

### 3. 先实现静态 HTML DEMO

- 根据原型图先写静态 HTML DEMO，而不是直接写正式前端页面。
- DEMO 应放在原型目录或任务指定目录，例如 `prototypes/admin/focused/v3/admin-focused-v3.html`。
- DEMO 使用真实 HTML/CSS/少量原生 JS 表达布局、状态和交互反馈；允许使用静态数据，不要求接真实接口。
- DEMO 的目标是视觉和交互语义校准：
  - 几何结构、间距、层级、密度
  - 字体、字号、字重、颜色、边框、圆角、阴影
  - 表格、筛选、卡片、表单、弹窗、抽屉、状态标签
  - 典型 hover、active、disabled、empty、error 状态
- 不要把整页原型贴成一张背景图。文字、按钮、表单、列表、表格必须是可检查的 DOM。

### 4. 截图对比和还原度评分

- 启动静态 DEMO，并用真实浏览器在目标视口截图。
- 将 DEMO 截图和原型图按同一视口、同一页面、同一状态进行对比。
- 主代理或独立评审子代理必须站在 UI 设计师角度评分，满分 100。
- 推荐评分维度：
  - 布局与几何比例：25 分
  - 视觉层级与信息密度：15 分
  - 字体、字号、字重和文案排布：15 分
  - 色彩、边框、圆角、阴影和质感：15 分
  - 组件状态与交互暗示：10 分
  - 原型关键细节覆盖率：10 分
  - 响应式和视口适配：10 分
- 评分达到 90 分及以上，静态 DEMO 才能作为最终开发实现参考。
- 评分低于 90 分时，必须列出差异清单，回到第 3 步继续优化 DEMO；不得进入正式前端开发。

### 5. 基于通过的 DEMO 产出 UI 设计说明

- 使用 `$prototype-to-ui-spec`，同时读取原型图、静态 HTML DEMO、DEMO 截图、对比结论和评分记录。
- UI 说明必须明确：
  - 哪些结构和 CSS 规则来自已验收 DEMO。
  - 哪些只是静态校准代码，不能直接进入正式工程。
  - 页面结构、组件拆分、状态矩阵、响应式规则、异常态和资产职责。
  - 正式工程里应复用哪些现有组件、接口层、路由和样式 Token。

### 6. 正式前端实现

- 正式实现以“原型图 + 90 分以上静态 DEMO + UI 设计说明”为共同约束。
- 优先迁移 DEMO 已验证的布局、间距、组件密度和视觉 Token，再接入正式工程的数据、路由、状态和接口层。
- 对复杂系统，先完成公共基础设施和核心页面，再按业务域切片实现；涉及仓库内 gitignore 外改动时，复杂任务应使用独立 worktree 派发子代理。
- 真实 DOM 负责文本、表单、按钮、导航、列表、表格和业务交互；静态资产只负责装饰、横幅、纹理或局部视觉质感。
- 不要在正式页面中保留静态 DEMO 的临时假交互、临时全局样式或与工程规范冲突的代码。

### 7. 正式验收与交付

- 至少完成一次项目构建或类型检查。
- 至少完成一次正式页面的真实浏览器截图验收，并和已通过的静态 DEMO 或原型图复核。
- 至少验证关键交互：
  - 导航和返回
  - 筛选、切换、展开、收起
  - 主按钮可用态和禁用态
  - 弹窗、抽屉、表单校验和提交反馈
- 对已有工程，额外扫描旧路由、旧交互、`alert(`、`confirm(`、临时 mock 入口和未跟踪副本文件。
- 合并到目标主分支后复跑必要验证；不要只在临时分支或静态 DEMO 中验收。
- 交付时说明：
  - 静态 HTML DEMO 路径
  - DEMO 截图与原型对比结论
  - UI 设计师视角评分和是否超过 90 分
  - UI 说明文档路径
  - 正式实现涉及的页面、组件和资产
  - 构建、浏览器和交互验证结果
  - 残留差异和下一步

## 强制规则

- 静态 HTML DEMO 是高还原流程的必经校准层。
- 未完成截图对比和评分，不得把 DEMO 作为正式开发参考。
- 还原度评分低于 90 分时，必须打回优化 DEMO。
- 不要用整页背景图冒充真实 UI；文本、表格、表单、按钮必须是 DOM。
- UI 说明必须基于“原型图 + 已验收 DEMO”，而不是只基于主观描述。
- 正式前端实现完成后，还要再做浏览器验收，确认工程实现没有偏离已通过的 DEMO。

## 触发示例

- “根据这份 PRD，先出高保真原型，再做静态 HTML DEMO，对比评分通过后把页面做出来。”
- “按 v3 原型先写 `prototypes/admin/focused/v3/admin-focused-v3.html`，截图对比 90 分以上再开发正式页面。”
- “我需要一条从需求文档到静态 DEMO、UI 说明、正式前端实现的完整工作流。”
- “页面必须高度还原原型，先让 UI 设计师视角打分，没到 90 分就继续改。”
