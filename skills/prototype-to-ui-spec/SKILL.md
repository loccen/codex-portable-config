# Prototype To UI Spec

将高保真原型图转成前端可直接落地的 UI 设计说明。默认输出中文，并优先服务前端开发交付，而不是设计评审文案。

对于高还原要求的页面，不要只凭原型图直接写最终开发说明。优先读取“已通过截图对比和 UI 设计师评分的静态 HTML DEMO”，把原型图与该 DEMO 的实现共同作为说明依据。静态 DEMO 还原度未达到 90 分时，只能输出问题清单和优化建议，不应把它作为最终开发参考。

## 核心原则

- 先观察，后推断。能够从原型直接读出的信息写成“已观察”，无法直接确认但为了交付必须补齐的信息写成“推断”或“待确认”。
- 用工程语言描述界面。优先写尺寸、层级、状态、规则、约束、交互、复用关系，不写空泛审美评价。
- 让前端能开工。输出必须覆盖页面结构、组件拆分、状态变化、样式 Token、响应式和交互规则，避免“按设计稿实现”这一类无效表述。
- 保持信息密度。面对多张原型图时，先抽公共规范，再写页面差异，避免重复抄写。
- 尊重校准结果。若任务提供静态 HTML DEMO、浏览器截图、原型对比图或还原度评分，必须把这些验收证据写入说明；未达 90 分的 DEMO 不得被当作开发基准。

## 工作流

### 1. 盘点输入

- 确认输入材料类型：单页原型、多页流程图、设计稿切图、带标注稿、混合截图。
- 统计页面/弹窗/浮层/组件态数量，建立页面清单。
- 识别端类型与场景：移动端 H5、原生 App、Web 后台、大屏等。
- 识别明显限制：是否存在暗色模式、是否有安全区、是否有底部 Tab、是否有悬浮操作、是否出现横向滚动区域。
- 如果存在静态 HTML DEMO，例如 `prototypes/admin/focused/v3/admin-focused-v3.html`，同时读取其 DOM、CSS、截图和评分记录，确认它是否已经通过 90 分门槛。

如果用户给的是一组连续原型图，先整理成“页面流”和“状态流”；不要逐张孤立描述。

### 2. 读取静态 DEMO 校准结果

当输入包含静态 HTML DEMO 时，先判断它的可信度：

- 必须有浏览器截图，而不是只看 HTML/CSS 源码。
- 必须和原型图做过同视口截图对比。
- 必须有主代理或独立评审代理站在 UI 设计师角度给出的还原度评分。
- 评分必须达到 90/100 及以上，才能作为最终前端开发说明的主要参考。

评分未达标时，输出应转为“问题清单 + DEMO 优化建议 + 重新验收要求”，不要继续产出最终实现规格。

### 3. 抽取全局设计语言

优先提炼整套界面的公共规范，再写页面明细：

- 色彩：主色、辅助色、语义色、背景层级、边框色、遮罩色。
- 字体：字号层级、字重、标题与正文差异、数字/标签/按钮文案的典型样式。
- 间距：常见外边距、卡片内边距、栅格/列间距、按钮高度。
- 圆角与阴影：卡片、按钮、输入框、弹层的规则。
- 图标与插画：线性/面性风格、尺寸规律、是否带容器底板。
- 组件复用：导航栏、搜索框、卡片、底部操作区、筛选条、表单项、浮层。

当原型没有标注精确数值时，用相对准确的工程表达，例如“主内容区左右边距约 16px，卡片圆角约 12px”。不要假装这些数值是设计师确认值。

当静态 DEMO 已通过 90 分门槛时，优先从 DEMO 的真实 CSS、布局层级和组件结构里抽取可落地规则；原型图用于校验视觉目标，DEMO 用于沉淀工程实现方式。

### 4. 输出页面级说明

为每个页面、弹窗、抽屉、底部面板补齐以下信息：

- 页面目标：这个界面解决什么任务。
- 信息结构：顶部区、主体区、辅助区、底部固定区分别承载什么内容。
- 布局说明：主轴方向、对齐方式、吸顶/吸底、滚动容器、层级覆盖关系。
- 组件拆分：页面由哪些可复用组件组成，各组件职责是什么。
- 样式规则：尺寸、间距、颜色、边框、圆角、字体等级。
- 状态规则：默认态、悬停态、激活态、禁用态、加载态、空态、错误态、选中态。
- 交互规则：点击、返回、切换、展开、收起、滑动、联动、反馈。
- 数据占位：标题字数、标签长度、图片比例、列表项密度、按钮文案长度约束。
- DEMO 对照：静态 HTML 中可复用的结构、CSS Token、布局技巧，以及不能照搬的临时代码。
- 开发备注：需要前端和产品/设计确认的风险点。

如果同一页面存在多个状态，优先合并成状态矩阵，而不是把同一页面重复写三遍。

### 5. 补齐前端落地信息

面向前端交付时，默认补齐这些工程信息：

- 页面路由或入口关系。
- 固定区与滚动区边界。
- 组件复用建议与拆分优先级。
- 建议的 DOM/组件层次。
- 资源要求：图片、图标、插画、透明背景、切图精度。
- 适配要求：最小宽度、断点策略、安全区、刘海屏、长内容处理。
- 文案溢出处理：单行省略、多行截断、超长按钮文案、空字段兜底。
- 异常场景：无数据、加载失败、图片缺失、接口慢响应。
- 静态 DEMO 迁移边界：哪些 CSS/结构可迁入正式工程，哪些只是为了原型校准而存在。

### 6. 标记不确定项

遇到以下情况时，明确标记而不是自行脑补定案：

- 页面跳转目标无法从原型确认。
- 图标含义不明确。
- 弹层关闭方式、提交成功反馈、表单校验规则未展示。
- 规格数值只能估算，无法确认设计基线。
- 同一组件在不同页面出现样式不一致，无法判断是否故意。

默认用“待确认”列出，并给出最合理的实现建议，便于前端先搭骨架。

## 输出要求

默认产出一份结构化 Markdown 说明文档。除非用户要求别的格式，否则按以下顺序组织：

1. 项目概览
2. 页面/状态总览
3. 全局视觉与交互规范
4. 页面级详细说明
5. 组件复用与拆分建议
6. 响应式与异常场景说明
7. 静态 DEMO 对照与迁移边界
8. 待确认项

页面较多时，先给“总览表”，再展开关键页面。不要一上来写长篇散文。

## 写作规范

- 使用面向实现的标题，如“商品卡片组件”“底部操作栏”“登录页空态”。
- 多用表格承载规则：状态、尺寸、间距、交互、资产需求。
- 区分“必须实现”和“建议实现”。
- 使用明确动词：显示、隐藏、固定、吸顶、截断、展开、回弹、禁用、置灰。
- 避免这些低信息表述：精致、好看、科技感、简洁大气、按常规实现、参考通用做法。

## 推荐模板

需要固定输出骨架时，读取 [references/spec-template.md](references/spec-template.md) 并按需裁剪，不要机械保留所有空标题。

## 质量检查

交付前自查：

- 前端是否能仅凭这份说明开始拆页面和组件。
- 每个关键页面是否都包含布局、组件、状态、交互四类信息。
- 是否把观察事实和主观推断分开写清楚。
- 如果存在静态 HTML DEMO，是否确认它有截图对比和 90 分以上评分。
- 是否把静态 DEMO 的可复用实现与临时代码边界分开写清楚。
- 是否覆盖了空态、加载态、禁用态等常见异常状态。
- 是否避免了把整份文档写成设计鉴赏或需求摘要。
